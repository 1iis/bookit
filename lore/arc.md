## Core traits

| Trait | Incarnated by / inspired by | Hyperbook meaning |
|---|---|---|
| **Augmentation**. | Douglas Engelbart. | Computers are not vending machines for answers. They are capability amplifiers. A hyperbook should leave the player more able to act in the world. |
| **Dynamic personal media**. | Alan Kay, Adele Goldberg, Seymour Papert. | The reader is not only a consumer. They should eventually become an author, modifier, explorer, and builder inside the medium. |
| **Explorable explanation**. | Bret Victor. | Concepts should be visible, manipulable, and responsive. If the book explains a system, the player should be able to touch the system. |
| **Deep hypertext**. | Vannevar Bush, Ted Nelson, Tim Berners-Lee. | A hyperbook is not merely pages in order. It is an addressable graph of resources, trails, references, transclusions, paths, and views. |
| **Composability**. | Ken Thompson, Dennis Ritchie, Doug McIlroy. | Small clear interfaces beat giant frameworks. A hyperbook runtime should have boring contracts: manifest, resources, state, capabilities, surfaces. |
| **Literate execution**. | Donald Knuth, Project Jupyter, fast.ai. / nbdev culture. | Explanation and instruction belong together. A hyperbook can be read, run, inspected, changed, and re-run. |
| **Visible trust**. | Butler Lampson, Saltzer & Schroeder, capability-security traditions. | Power must be legible. If a hyperbook wants files, network, AI, shell, camera, or secrets, the player should see the contract. |
| **Physical-media dignity**. | Game cartridges, CDs, DVDs, consoles, studio media formats. | The hyperbook should feel ownable and portable. Source is the cartridge; personal state is the save file. |
| **Play as intelligence**. | Papert, Montessori-adjacent traditions, great game designers. | A "game" is structured action with feedback. Learning should feel like serious play, not institutionalized boredom. |
| **Fourth-wall bridge**. | HyperCard, Unix tools, web APIs, modding culture, maker culture. | The book world and real world can meet. Real files, real APIs, real dashboards, real objects, real consequences — with consent. |
| **Progressive enhancement**. | Web architecture, graceful degradation, old robust systems. | Start as text. Wake up in layers: images, audio, interaction, code, AI, live data, local state, world integration. |
| **Preservation and forking**. | Archivists, open-source culture, Internet Archive, Git. | A hyperbook should be inspectable, preservable, forkable, movable, and not trapped in one corporate surface. |

## Feats

| Feat | Description |
|---|---|
| **Manifest Oath**. | Every powerful medium begins with a clear contract. The player should know what this hyperbook is, what it can do, what it wants, and what it may touch. |
| **Savefile Doctrine**. | Source and player state must remain separate. The cartridge is portable; the save is personal. Both can move, but they are not the same object. |
| **Fourth-Wall Bridge**. | A hyperbook may cross into reality: real files, real APIs, real sensors, real accounts, real dashboards — but only through visible, reversible gates. |
| **Text First, World Later**. | A hyperbook should boot as text if nothing else is available. Every richer layer is enhancement, not a hostage situation. |
| **Tiny Loop Discipline**. | Do not build the cathedral first. Make one manifest, one entry, one rendered resource, one state boundary, one action. Then grow. |
| **Player Sovereignty**. | The player owns their notes, progress, generated artifacts, preferences, and local modifications. The medium should not eat the player. |
| **Inspectable Magic**. | AI is allowed, but fog is not. Show prompts, model calls, inputs, outputs, costs, diffs, provenance, and uncertainty where relevant. |
| **Serious Play**. | Games are not decoration. A game is a truth engine: situation, action, feedback, consequence, mastery. |
| **Graph Sight**. | Linear order is only one view. A hyperbook may expose trails, maps, prerequisites, scenes, timelines, concepts, missions, and alternate routes. |
| **Forking Blessing**. | If a reader understands the work deeply enough to change it, the medium has succeeded. |

## Bio

Arthur Rowan Calder learned computers backward.

As a child, he did not first meet a computer. He met broken radios, paper manuals, library cards, cassette tapes, circuit diagrams, and old machines that only worked if you understood what each part was trying to do. His grandfather repaired farm equipment; his mother kept notebooks full of recipes, bills, letters, and weather records; his first lesson in computing was that information only matters when it helps someone do something.

In the 1970s, ARC discovered time-sharing terminals and became obsessed with one fact: a screen could answer back. Not merely display; respond. A document could become a place. A command could become a tool. A tool could become a habit. A habit could become a new kind of person.

He spent the next five decades moving between labs, schools, studios, archives, game companies, and small businesses. He worked on educational systems that were too early, hypermedia systems that were too isolated, game tools that were too proprietary, web systems that became too distracted, and notebooks that came closest to what he had always wanted: documents that could think with you.

His private complaint was always the same:

> "We keep making sealed boxes for living ideas."

To ARC, the hyperbook is the missing synthesis.

Not an ebook.  
Not an app.  
Not a website.  
Not a game.  
Not a notebook.  
Not a course.

A hyperbook is the thing those were all trying to become when the subject demanded more than passive reading.

## ARC's one-line creed

> A hyperbook is a playable bridge between media and reality, built so the player can inspect the bridge.
